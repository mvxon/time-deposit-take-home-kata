# 0004. Paged balance update in a single transaction

## Context

The balance update has to process every deposit. Loading the whole table at once does not scale, and sending one `UPDATE` per row is slow.

## Decision

- Read deposits in pages using keyset pagination (`id > last id`, page size `time-deposit.balance-update.page-size`, 1000 by default). For each page: calculate, flush the changed balances, clear the persistence context. Memory holds at most one page.
- Send updates in JDBC batches (`hibernate.jdbc.batch_size: 100`, `order_updates: true`) and write only changed columns (`@DynamicUpdate`): `update time_deposits set balance = ?, version = ? where id = ? and version = ?`.
- Process all pages in one transaction, so an update is all-or-nothing. A conflict on any page rolls back every page (`rollsBackEarlierPagesWhenALaterPageConflicts`).
- The transaction boundary is in the persistence adapter, on the port operation `updateBalancesAtomically`. It is a unit of work, like Spring's `TransactionTemplate`: the adapter owns the paging and the transaction, and the domain logic (the calculator) is passed in as a `Consumer`. The reason is that `TimeDeposit` is a shared class that must not change, so the domain has nowhere to carry the version read for optimistic locking. Between reading a page and writing it, the version lives in the JPA persistence context, which is safe only when both happen inside one transaction controlled by the adapter. So optimistic locking and atomicity do not depend on how the caller invokes the operation, and the application service has no transaction annotations.
- Integration tests use a page size of 2, so every test exercises several pages.

## Alternatives rejected

- **Transaction in the application service**, with port operations `findPageAfter(lastSeenId)` and `saveBalances(deposits)`. The use case would show every step, but `saveBalances` would be correct only when called in the same transaction as `findPageAfter` and before the persistence context is cleared — a temporal coupling the compiler cannot check. If a caller loaded and saved in different transactions, the adapter would read the current version at write time and a concurrent change would be silently overwritten. The safe form of this alternative returns a versioned snapshot from the port (for example `VersionedTimeDeposit(deposit, version)`) and writes `update ... where id = ? and version = ?` explicitly; that adds a technical field to the domain model and more code, which one use case does not justify.
- **A transaction per page** bounds the transaction length, but a failure halfway leaves some deposits with interest and some without, and a retry applies interest twice to the first part. It becomes safe only with the period guard from [0003](0003-accrual-responsibility-and-idempotency.md).
- **A single set-based `UPDATE`** would be fastest, but PostgreSQL computes in exact decimals and cannot reproduce the legacy `double` rounding ([0001](0001-preserve-legacy-calculation.md)).

## Consequences

- Memory use is bounded and the number of database round trips is small.
- The transaction is as long as the whole run and holds row locks on updated deposits until it commits; any concurrent change to a deposit makes the run fail with `409`. For very large volumes the next step is a batch job (for example Spring Batch) with the period guard and per-chunk transactions.
- The use case cannot add another write to the same transaction (for example an audit record or an outbox event). If that becomes a requirement, the transaction moves to the application service and the port returns the versioned snapshot described above.
- Known limitation: `GET /time-deposits` still loads all deposits with their withdrawals in one query. For large volumes it would need pagination parameters (still one endpoint).
- Ids are generated by identity columns. The service never inserts rows; if it did in bulk, a sequence with an allocation size would allow batched inserts.
